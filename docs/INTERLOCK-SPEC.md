# EMU-1 boarding bridge — proposed runtime interlock specification

**Status: proposed handoff to CODE · vector, not implemented or safety-approved.** This does not change a shared contract or authorize live use. EMU-1 contains eight individually mounted, stowed bridge plates. Blender samples cover one manually deployed pose only; no runtime movement, Studio physics, passenger safety or device test has been proven. This spec defines the minimum behavior and headless acceptance vector should implement; Manager must approve new API/config values and engineering must verify the motion path and collision behavior before service.

## Source of truth and current gap

- Geometry: `assets/trains/EMU-1/INTEGRATION.md`, `assets/trains/EMU-1/verify_vehicle_bridges.py`, `docs/ASSET-INTERFACES.md` and `src/shared/Contracts/GeometryContract.luau`. `docs/DIMENSIONS.md` was absent in the fetched branches when this was written; confirm whether a newer document supersedes the ratified sources before accepting dimensions.
- At `f5c71ed`, each car root has `CAR_SIDE_BRIDGE_N_PIVOT` (`CAR` = `CAB` or `INTERMEDIATE`; `SIDE` = `L` or `R`; `N` = 0 or 1), with separate `..._VISUAL` and `..._COLLISION` children. The collision suffix is `_COLLISION`, not necessarily `_COLLISION_`. Eight bridges must be discovered independently. Check imported axes, names, pivots, animation and assembly ownership; do not assume Blender hierarchy survives a Roblox import unchanged.
- Plate dimensions 1.10 × 0.26 × 0.04 m; 1 m = 3.5714286 studs. Car-local stow pivot = (door centre X, ±1.47 m, 0.70 m above rail); full deployed displacement = 0.18 m outward + 0.04 m up (0.642857 + 0.142857 studs). Fully stowed max half-width 1.60 m; deployed outer edge 1.78 m, beyond the 1.60 m running half-envelope, crossing the nominal 1.70 m platform-edge datum. Direction must be transformed through the validated car-local basis, not hard-coded world X/Z. These are endpoints, **not an approved motion trajectory**; the stowed plate is inside the footboard, and interference during any movement must be resolved before enabling it.
- The train GLB's default stowed pose still leaves ~0.10 m unsupported at the sampled platform. One manually translated aligned, level deployed pose had 0/423 missing point samples. This is neither continuous coverage nor proof of safe boarding. Until all controls and actual geometry/physics validation are complete, keep the feature disabled and preserve movement inhibition on unknown bridge state.
- Vector's `origin/vector/rail-core` at `5d62a19` owns a server-authoritative 30 Hz `TrainService` and currently advances door state and dwell without this bridge interlock; its station-arrival `speedMs <= 0.5` snap and existing door-state string are **not** standstill, platform-fit, bridge-sensor or safe-departure proof. Its dwell completion cannot clear the stop or release traction before the required acknowledgements below.

## Proposed server-internal API (not an existing contract)

Implement a pure deterministic `BridgeInterlock.step(previous, input, config) -> (next, effects)` under vector's ownership, plus a Roblox adapter. No new client remote or shared-contract field is ratified by this document. The reducer runs once per authoritative train tick *before* motion/door decisions, and may be iterated to a stable decision for same-tick feedback; the adapter applies commands and samples fresh acknowledgements. Never trust client-side collider state or client-supplied platform, motion, occupancy or actuator assertions.

**Per train input** (every item absent/unknown/stale/invalid is unsafe): monotonically sequenced server tick/time, train identity, current car roots/assembly health, measured signed speed and standstill confirmation, movement/brake/door intent, authoritative brake-hold feedback, selected station/stop and side, stop/platform identity and fresh per-door platform alignment + clearance evidence, door-leaf states/closed-lock feedback, sensor health, doorway/plate occupancy-clear proof, emergency/fault status. A platform-fit result must account for the **particular door**, lateral, vertical and longitudinal tolerances, plate overlap at both ends, track/cab orientation, station edge geometry and verified free travel. A boolean generated solely from `stoppedAtStation`, a schedule marker or client signal is insufficient.

**Per bridge feedback**: stable bridge ID; stowed and deployed limit/position confirmations, actuator health and completion/fault; authoritative collision and attachment readback; sensors/occupancy health; source tick/time and sequence. Conflicting limits, missing nodes/proxies, stale or out-of-order observations are invalid. Infer neither `stowed` nor `deployed` solely from a command or animation timer. Sensor timeouts, minimum dwell, position tolerances, exact standstill/brake criteria, valid swept path and occupancy detection are **approval-required configuration**, not invented defaults: missing/unapproved config means disabled, no deployment and no traction release if bridge safety is unknown.

**Outputs/effects**: per-bridge target (`hold`, `deploy`, `retract`), plate collision command, boarding-permit flag, door command/gate, train traction/departure permit, hold/brake request, and latched fault code with bridge ID. `CanDepart` is an aggregate for *all* mounts, not only selected doors. Effects must be applied idempotently with a sequence/epoch so duplicate, delayed or prior-trip acknowledgements cannot make a new cycle safe. Server logs should carry train/bridge ID, transition, reason and tick without spamming each frame. Clients may receive read-only status via a separately approved contract; they cannot override interlocks.

## Required sequence

1. **Initialize / spawn:** before exposing the assembly to players or enabling physics, discover all eight mounts, enforce visual `CanCollide=false`, keep each bridge proxy non-colliding and command/verify stow. Lock out boarding, traction and departure until fresh, independent stowed/attachment/health confirmations for all bridges exist. On missing feedback do not infer stow. Fail safe on attach, weld, ownership, streaming or initialization failure.
2. **Approach and hold:** all bridges confirmed stowed with proxy collision off; all train doors confirmed closed and locked; no faults; traction permission is an explicit result of these facts and normal train signalling. At a stop, establish standstill and held brake from fresh authoritative measurements; do not treat an arrival snap or requested brake as evidence. If stop is on an unsupported side or any selected doorway has no verified platform fit/approved clearance, keep that doorway and its plate closed/stowed; default to denying boarding.
3. **Open and prepare:** only after stop, hold, station, side, fit, attachment, path and occupancy checks pass may the selected door(s) open. Hold traction throughout. Opening a door is not permission for a passenger to cross an unsupported gap: gate boarding/access at that doorway until its own bridge is stable, confirmed deployed and its collision acknowledgement is valid. Non-platform side stays closed, stowed and non-colliding. Prove the gate works physically, not just via UI/remote state.
4. **Deploy:** with door open and doorway/plate path confirmed clear, command only the eligible bridge's validated trajectory to its deployed endpoint. Keep proxy collision **off during movement**, boarding gate closed, and train held. Position confirmation must be fresh and independently observed at the final endpoint; a timer is not sufficient. After all safe-to-enable checks remain true, enable that bridge proxy and verify collision readback; only then grant that door's boarding permit. Visual mesh remains non-colliding. If geometry or occupancy cannot be checked, do not deploy.
5. **Close / retract:** stop new boarding; wait for verified clearance, close and positively lock the selected door without trapping anyone, while train remains held and any plate supporting a passenger remains fixed. Only once door lock, occupancy clearance and approved path checks are confirmed may the controller disable proxy collision, verify it off, command retraction, and verify the plate at stow with attachment intact. Re-enable neither collision nor boarding during retraction. If any bridge is obstructed, unknown or fails to retract, hold the train and latch a fault; never bypass on dwell expiry.
6. **Depart:** permit traction and departure only when **every** bridge on both sides is freshly confirmed stowed, healthy and attached, every bridge proxy collision is verified off, every door is closed/locked, no fault or emergency is active, and all normal signalling/braking conditions allow it. An unselected, disconnected or unknown mount blocks release. Dwell timer expiry, an open-door animation finishing, or a requested retract alone never grants permission.

The order above is a functional requirement, not a validated mechanical design. In particular, neither straight-line interpolation nor raising-first has been proven to clear the fixed footboard/platform. The adapter must remain disabled until an approved swept geometry and collision plan exists.

## Collision, failure and recovery invariants

- Visuals never collide. No bridge proxy may be enabled during motion or in the stowed/partial state; enabling requires a verified fully deployed, held, platform-fit pose. A stale or missing collision readback is not an acknowledgement. Do not enable all eight proxies just because one door is open.
- Never remove support under a detected or possibly present passenger merely to satisfy a departure or fault transition. If a condition fails after support was enabled, latch fault, prohibit new boarding/departure, request brake/traction cut and hold the plate and its already-enabled support **only while its pose remains confirmed stable**. Obtain an approved occupancy-clear/recovery procedure before disabling or moving it. If physical drift, platform movement, lost feedback or actuator movement makes stable support uncertain, request emergency braking and emergency response; this spec cannot guarantee passenger safety in that condition. No automatic retract or blind collider toggle in a fault.
- Contradictory sensors, unexpected motion, lost alignment or hold, stale packets, nonfinite numbers, unknown occupancy, obstructed motion, actuator timeout, unauthorized remote intent, desync, despawn/restart/streaming loss and missing configuration deny boarding and departure, latch fault and request hold/brake. Emergency brakes must not be weakened or delayed by this interlock. Never automatically clear a latched fault after timeout or stale data recovery; a server-authorized recovery requires fresh health/occupancy/position evidence and a controlled, tested stow sequence, then verified closed/locked doors and all proxies off.
- Within one server tick evaluate feedback and movement permissions atomically: on a new fault, traction must be inhibited **before** integration can move the train. Initial replication must not briefly expose colliding bridge proxies. After restart treat unknown as unknown; do not restore last `deployed`/`stowed` from a client snapshot. Respect actual server physics ownership and network-latency failures.

## Headless acceptance for vector

Implement a pure reducer and mocks as above, register a new `tests/rail/bridge_interlock.spec.luau` in vector's `tests/run.luau`, and run `lune run tests/run.luau` from the vector branch. That is the existing headless Lune runner; the new spec does **not** exist yet. Assert exact state/effects, train-wide departure and collision invariants on every tick, not merely final state. At minimum cover:

1. Spawn with all 8 healthy and independently confirmed stowed/off: no departure before acknowledgement; allow only after all closed/locked and healthy. For each individual missing/partial/contradictory/stale mount or missing config, deny release.
2. Intended-side stop: open selected door, deploy only after valid stop/hold/fit/clear inputs, collision off throughout movement, enable only after confirmed deployed, boarding only after collision acknowledgement. Verify four door positions and both sides/cars; non-platform side stays shut/stowed.
3. A valid close cycle: gate boarding, prove clear, close/lock, collision off acknowledgement, retract, confirmed stow, then aggregate all-eight departure permission. Dwell timeout alone cannot skip a stage. Repeated inputs and duplicate acknowledgements must be idempotent.
4. Parameterized denial: positive or negative speed outside approved standstill, failed hold, wrong platform/side, each fit axis out of tolerance, missing route clearance, opening/closed/closing door, obstacle or unknown occupancy, unavailable sensor, partial pose, conflicting limit switches, unhealthy weld/actuator, missing/misnamed proxy and nonfinite values. No deploy/boarding/traction on unsafe input.
5. For each phase, inject lost stop/hold/fit, stalled actuator, sensor timeout, stuck collider, emergency, restart, despawn, streaming loss, out-of-order/duplicate/old-epoch acknowledgement and unauthorized client command. Assert same-tick brake/traction inhibition, fault latch and no unsafe plate movement; a passenger/unknown occupancy with stable deployed support must not trigger an automatic drop of support or blind retract. Recovery requires explicit authorization and new verified evidence.
6. Race/property tests over varying tick order, request bursts and per-door asynchronous feedback: assert `CanDepart => all8(stowed AND collisionOff AND healthy) AND allDoorsLocked AND noFault`; `BoardingPermit[door] => sameDoor(deployed AND collisionOnAck AND platformFit AND doorOpen) AND standstill AND hold`; `plate moving => collisionOff AND boardingDenied AND tractionInhibited`. Model unknown/stale as false and verify these implications after every transition.
7. Exercise normal existing vector rail/door/backpressure tests together with the new tests; verify the stop/dwell integration cannot release the hold on timer expiry until the reducer grants `CanDepart`. These pure tests do not replace a Roblox adapter/integration test.

For art-side reproducibility, run the existing GLB/FBX mount and representative seam checks documented in `assets/trains/EMU-1/INTEGRATION.md`. Headless tests only establish logic and sampled geometry. Before operational acceptance, additionally verify actual import/assembly, collision transitions, motion clearance, moving door interaction, humanoids, occupancy sensing, multi-user/network failure and accessibility in an authorized test environment; mobile/emulator and physical-device rows are deferred to the Director device session.
